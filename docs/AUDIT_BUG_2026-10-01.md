## 1. SQL executor exposed to the public — CRITICAL

`sql_simple_query` (migration 0059) is a **generic SQL executor**:

```sql
EXECUTE 'SELECT COALESCE(json_agg(row_to_json(t)), ''[]''::json) FROM (' || query || ') t'
```

Two things that combine into something fatal:

1. **`SECURITY DEFINER`** — it runs as the function owner, so it **does not apply RLS**
2. **Default grant to `PUBLIC`** — PostgREST exposes it to `anon` and `authenticated`

The Supabase anon key **is in fact public** — it's sent to the browser by design. So this isn't
"you need an account", it's **anyone who opens the site can run arbitrary SQL**:

```sql
select * from users          -- email, wallet, role
select * from secret_vault   -- encrypted credentials
select * from wallet_txs     -- the entire transaction history
```

**Fix (0077):** revoke from `public`/`anon`/`authenticated`, grant only to `service_role`,
plus pin `search_path` (without that, an attacker who can create objects in an earlier schema
can hijack unqualified references inside the function).

## 2. 51 of 52 SECURITY DEFINER functions can be called by anon

After #1 was found, I checked **every** function. The result:

```
total SECURITY DEFINER functions : 52
callable by anon/auth           : 51
```

Including the ones that **move money**:

- `treasury_payout_atomic`
- `settle_wl_deal_after_timeout`
- `slash_wl_deal_noncustodial`
- `restock_instant_order`, `send_order`, `update_product_variants`

They're all `SECURITY DEFINER` → **RLS bypass**. This isn't just a read leak; it's a
write surface exposed to the public.

**Fix (0078):** mass revoke (not a list of names, so new functions stay protected if the
migration is re-run) + grant `service_role`.

**Why it's safe:** the browser **never** talks to Supabase directly — there's no
supabase-js in `public/`. All access goes through API routes using the service role key,
which does bypass RLS.

## 3. Eight tables without RLS

```
RLS on  : 29
RLS off :  8   ← currency_rates, indexer_state, lifecycle_events,
                   product_stock_items, reconciliation_queue, reports,
                   temp_reset_codes, user_currency_preferences
```

All eight still have full DML grants (SELECT/INSERT/UPDATE/DELETE/TRUNCATE) to `anon`.
The most serious: **`temp_reset_codes`** — password reset codes.

**Fix (0078):** enable RLS on all tables + a verification block that `RAISE EXCEPTION`s
if anything is still exposed. A migration that fails silently is how this hole has
survived all along.

## 4. Auto-release completely dead

`app/api/orders/[id]/auto-release/route.ts` — its first query:

```ts
.select(`id, status, amount, buyer_fee, on_chain_order_id,
         on_chain_tx_hash, settled_at, settlement_tx_hash, ...`)
```

`orders` **does not have** `settled_at`, `settlement_tx_hash`, or `auto_released`.
PostgREST rejects the query → `order` is null → the route responds with **404 "Order not found"**
for **every** order.

So the auto-release cron (which releases funds after the buyer goes silent) **never
succeeded even once**. Its write would fail too — but the read already failed first.

**Fix (0075):** add the three columns + backfill `settled_at` from `updated_at` for
orders that were already released. **The backfill hit 4 stuck orders.**

## 5. Gateway EOA completely broken

`lib/circle/gateway-eoa.ts` was adapted from another repo (`arc-multichain-wallet`) whose
**schema is different**. Four problems:

| | Problem |
|---|---|
| insert | writes 5 phantom columns: `name`, `wallet_address`, `blockchain`, `type`, `wallet_set_id` |
| read | `.eq("type", "gateway_signer")` — the column is `wallet_type` |
| source | reads `wallet_set_id` from the DB — but that's config (`CIRCLE_WALLET_SET_ID`) |
| error | `catch {}` swallows **all** errors → a schema bug surfaces as "wallet doesn't exist yet" |

That last point is what kept this bug hidden: a broken query is treated as
"no wallet yet", then the code tries to **create a new wallet** — and fails too.

**Impact:** 4 routes dead — `/api/wallet/gateway/{balance,deposit,transfer,withdraw}`.

## 6. Seller profile never appears

## 7. `orders.status = 'RELEASED'` — a value outside the CHECK constraint

After the settlement columns were added (#4), auto-release **still failed** — because
the `status: 'RELEASED'` it writes **isn't in the CHECK constraint**:

```
orders_status_check: PENDING | PROCESS | SENT | DONE | DISPUTED | CANCELLED | DECLINED
```

The correct terminal status is **`DONE`** — that's what the buyer-confirm path
(`orders/[id]/confirm`) and `auto-settlement.ts` use.

So there are **two layers of bugs in the same route**: a missing column (#4) *and* a wrong
enum value (#7). Fixing only the first isn't enough.

Bonus: the guard `if (order.status !== 'DONE' && order.status !== 'RELEASED')` accepts a value
that **cannot possibly exist** in the DB — a dead branch. Already cleaned up.

## 8. `wallet_txs.method = 'external_transfer'` — a value outside the CHECK constraint

```
wallet_txs_method_check: qris | card | bank | onchain | cctp | internal | onchain-ucw
```

The admin treasury withdrawal route writes `external_transfer`, which **isn't in the list** →
the insert is rejected → **the treasury withdrawal can never be recorded**. Because that record
is what gets polled for status, the withdrawal appears to hang rather than fail clearly.

The correct value: **`onchain-ucw`** — the transfer goes through the Circle UCW SDK, and that's
also the value keyed by `lib/wallet/reconcile.ts` to complete the challenge.

## Latent gap: `payment = 'Langsung'`

The `orders.payment` CHECK allows `Saldo | Langsung | Onchain`, but the draft cleanup only
has a reaper for **`Onchain`** and **`Saldo`**. If a `Langsung` row ever enters the `PENDING`
state, it **will never be cleaned up**.

Currently **latent, not an active bug**: `'Langsung'` is only declared in the `PaymentMethod`
type (`lib/types.ts:46`) and is never written to the DB — of the 20 existing orders, only
`Onchain` and `Saldo`.

Closed with an **invariant test**: if `Langsung` ever starts being used, the test fails and
forces its reaper to be added.

## 9. Reconcile job reports noise forever

`reconcileMissingOnchainIds` scans orders that have `on_chain_circle_tx_id` but whose
`on_chain_order_id` is still NULL — so that escrows whose relay was submitted but whose
contract id failed to be read can be recovered.

The problem: it **also** scans orders that are already done. Four orders in the DB have
`status = DONE` and `on_chain_status = RELEASED` — **already settled**, their contract id
is just a historical value. But on every run the job still tries to resolve, fails, and logs a warning:

```
{"ran":true,"ordersResolved":0,"dealsResolved":0,"stillPending":4}   ← forever 4
```

**Why this matters:** a metric that **can never be silent is useless**. If
`stillPending` is always 4, the orders that are genuinely stuck get drowned in the noise — and
it's precisely those stuck orders that need attention.

Bonus: every run wastes 4 resolve attempts that are guaranteed to fail.

**Fix:** add `.not("on_chain_status", "in", "(RELEASED,REFUNDED)")` to the order scan
**and** the deals scan — skip what's already settled on chain.

Result:

```
stillPending : 4 → 0
job duration : 3044ms → 50ms   (60× faster)
```

## 10. Referral history will never appear

`GET /api/referral` returns:

```ts
history: data.history ?? [],   // `referrals` does NOT have a `history` column
```

The value is **always** undefined, so the API **always** answers `history: []`.
`public/referral.jsx` renders the invitation list from that — meaning the
**"Your Invitations" section shows an empty state forever**, even for users who
have invitations.

The data source actually exists: the **`referral_events`** table
(`referee_uid, reward, status, created_at`).

**Fix:** read `referral_events` by `referrer_id`, join to `users` for
name + avatar, and map the status `done → "verified"` (the UI speaks `verified|pending`,
the DB speaks `done|pending`).

Verified with real data — before: `history: []`; after:
`history: [{user:"Member", avatar:null, date:"...", status:"verified"}]`.

### Lesson: a test that locks in the bug

There's an old test that actually **enshrines** this bug:

```ts
it("GET tolerates a missing row instead of throwing", () => {
  // `history` is also read back on GET — it must be defaulted, not required.
  expect(CODE).toMatch(/history:\s*data\.history\s*\?\?\s*\[\]/);
});
```

The assertion was written from the perspective of "this code should be like this", not
"the system should behave like this" — so it stays green forever while the feature is dead.

**An assertion must state an invariant, not an implementation.** Already replaced.

## Tooling left behind

**`scripts/check-select-columns.mjs`** — cross-checks every column reference in
`.select()`, `.insert()`, `.update()` and filters (`.eq`, `.order`, `.not`, …) against the
real schema, **plus every value written to a CHECK-constrained column**.
**1.981 references + 20 enum tables checked.**

This is what found bugs #4, #5, #6, #7, #8 — five of eight.

```bash
node scripts/check-select-columns.mjs
```

> **Note on writing this script:** it took 3 iterations to eliminate false positives —
> (1) relation names like `users`/`stores` were read as columns, (2) `.select` from a
> different query chain was also read, (3) `.insert` payloads were attributed to the
> previous `.from`. The finding count dropped step by step: **62 → 35 → 5 → 2 → 0**.
> This kind of script easily produces noise that ends up hiding the real bugs.
>
> Same goes for the enum check: `method: "instant_items"` and `"manual_qty"` were briefly
> flagged, even though both are in the **JSON response** (`jsonOk({...})`), not a DB write.
> The enum check must be limited to write payloads only.

**`scripts/probe-routes.mjs`** — probes **all 153 routes** against a server that's actually
running, classified by **content-type** (not status code — the catch-all frontend route
answers nonexistent `/api/*` paths with **HTML 200**, which looks like success).
The most important classification: **`500 body kosong`** — the sign of a handler throwing before
its own `try/catch`.

```bash
node scripts/probe-routes.mjs
```

**`scripts/run-jobs.ts`** — runs every scheduled job once and prints **both the status AND the
result body**. Jobs are the least-tested code: no normal usage triggers them, and a cron that
forever reports `{"scanned":0}` **looks healthy** while doing nothing. A job that "succeeds"
with a suspiciously empty result is exactly the signal.

```bash
node --env-file=.env.local --import tsx scripts/run-jobs.ts
```

**`__tests__/lib/bug-hunt-regressions.test.ts`** — 12 tests that lock in the invariant
(the right columns, valid enum values, grants that must not be public, cleanup that covers
every entry state, reconcile that can be silent), not the incident.

## 11. Session is never restored (THE BIGGEST BUG)

**Symptom.** A user who has a **valid** session cookie but an empty `localStorage` — a new
browser or device, incognito mode, after "clear site data" — **always sees the sign-in page**.
Deep links to `/admin`, `/orders`, `/wallet` all bounce to sign-in.

**Root cause.** In `public/app.jsx`:

```js
const [authed] = useState(() => localStorage.getItem('slime_authed') === '1');

useEffect(() => {
  if (!authed) return;                 // ← circular gate
  fetch('/api/auth/me', ...)           // which should restore the session
}, [authed]);
```

`slime_authed` is written **only** by the sign-in handler. So the restore only runs
if `localStorage` already proves you're logged in — but that's exactly the state
being restored. The session cookie is `httpOnly`, so JS can't see it.
A vicious circle.

**Fix.** Remove `if (!authed) return;` — that call **itself** is the test for "am I
logged in". And set `authed = true` when the restore succeeds, so the other `if (!authed)`
gates (notifications, orders) also open without a manual sign-in.

**Evidence.** Before: 20 seconds, only 3 requests (`/api/products` ×2, `/api/health`) —
`/api/auth/me` was **never** called. After: it's called, `ME.role = "Admin"`,
`ME.uid = "MSA6"`, the page renders.

## 12. Landing page 401 on every visit

`landing.jsx` calls `/api/sales/recent` for the sales ticker, but that endpoint
isn't in `PUBLIC_API_PREFIXES` → **401 every time a visitor isn't logged in**. The code
does handle that failure (fallback to a static list), but as a result the ticker
**will never** show real data, plus one console error on every load.

**Fix.** Add `/api/sales/recent` to the allowlist. Safe: `getRecentSales` already
anonymizes buyers (`buyerAnon` via `censorName` → `"John***"`) and only
returns the product/store name, amount, and time.

|---|---|---|
| zh | `首页 / 首页` | `首页 / 落地页` |

### i18n structure (for reference)

`DICT` has 4 blocks (`en@21, id@221, zh@1060, ru@1896`) with **907 keys**. The `en` block
only holds **311 keys** — the rest aren't required, because `tr()` falls through:


It's been verified that **no key risks showing up raw**: every key called without a fallback
argument exists in `DICT.en`. The ones that at first glance looked risky
(`nav.`, `pm.`, `home.cat.`) turned out to be false positives — they're template literals
(`tr('nav.' + x)`), not literal keys.

## 15. Clicking the "Overview" tab crashes the app

**Symptom.** Clicking the **Overview** tab in the Admin Console → the whole page is replaced by a screen:

```
Something went wrong
Cannot read properties of null (reading 'collectedFees')
```

The user has to click "Reload App" to recover. The error boundary catches it, so
`window.onerror` is **not triggered** — this defect is only visible via screenshot.

**Root cause** (`public/admin.jsx` lines 705 & 718) — a JSX expression that is **half
guarded**:

```jsx
{treasuryData ? (…platformFee…) : '—'} {treasuryData && '+'} {treasuryData.collectedFees?.gasPool ?? 0}.00 USDC
                   ↑ ternary guards this   ↑ guard fragment     ↑ BUT THIS IS EVALUATED UNCONDITIONALLY
```

The ternary only protects the **first** expression. The **second** expression — after
`{treasuryData && '+'}` — is evaluated unconditionally, so `treasuryData.collectedFees`
blows up while `treasuryData` is still `null` (the state before `/api/admin/treasury` finishes).

**Fix.** `treasuryData.collectedFees` → `treasuryData?.collectedFees` (two lines).

**Verification.** Before: clicking Overview = crash. After: **12/12 tabs OK**, and the content
size of each tab now differs (593–1552 char) — proof that the tabs really do swap content.

> **Lesson.** A half-finished guard is more dangerous than no guard at
> all: `x ? A : B` next to `x && C` reads as already safe, even though `D` behind
> it is still evaluated. And because the error boundary swallows it, this failure doesn't
> show up in the console — it's only visible if the page is actually rendered and looked at.

## 16. Checkout shows two different balances under the same label

**Symptom.** The "Slime Wallet" payment tile shows **49.00 USDC** (the platform ledger
balance), but the payment gate in the same modal reads **"On-chain Balance
0.00 USDC"** and its button says "Insufficient Balance". A user with funds on the platform
but zero on-chain sees the app say "you have funds" and then immediately say
"you don't".

**Root cause** (`public/storefront.jsx`). The tile shows `ME.usdc` (ledger balance),
while the gate uses `balanceForGate` = `ME.usdcOnChain` (on-chain Arc balance).
The gate is **in fact correct** — the server verifies the on-chain balance; there's a comment explaining why. What's wrong is the tile: the number it advertises isn't the
number that gets checked.

**Fix.**
1. The tile uses `balanceForGate` — the same source as the gate.
2. The i18n label `sf.walletBalance` is changed to **"On-chain Balance (Arc)"** (en/id/zh/ru
   plus its default fallback), so it no longer matches the unlabeled ledger number in the
   header.

**Verification.** Tile "Slime Wallet 0.00USDC" = gate "On-chain Balance (Arc)
0.00USDC" = button "Insufficient Balance". Consistent.

> **Lesson.** Two numbers from two different sources both called "Wallet Balance"
> is a UX bug even when the payment logic is correct. If the gate must use the on-chain
> balance, every place that shows a balance for a buy decision must use the same
> source, and the label must name that source.

## 17. Products with per-variant stock cannot be bought at all

**Symptom.** Buying a product whose stock is per-variant always fails:

```
POST /api/orders → 400
{"error":"checkout RPC failed: insufficient stock (have 0, want 1)"}
```

Even though the storefront shows the stock correctly (e.g. the "Default · 9" variant).

**Root cause.** There are **two stock stores** and each order path only
understands one of them:

| Store | Filled by | Read by |
|---|---|---|
| `products.stock_items` (text[], migration 0003) | sellers who don't use variants | `create_order_atomic` (custodial) |
| `product_stock_items` (migration 0037) | `createProduct` when the seller fills per-variant stock | `create_non_custodial_order` |

`createProduct` writes to `product_stock_items` and **empties** the old array. So a
product with per-variant stock has `stock_items = {}` → `pop_stock_fifo` sees 0 →
always fails. Conversely, old products (stock in the array) fail on the non-custodial
path. These two paths are mirror images of each other.

Worse still: `pop_stock_fifo_variant` and `stock_count_variant` were introduced by
0037, but **not a single order path calls them** — that "new" stock mechanism is
write-only.

**Fix (migration 0079).**
- `pop_stock_fifo_auto(product, variant, qty)` — picks the right pop: use the
  per-variant table if it has rows, otherwise fall back to the old array.
- `pop_one_stock_item(product, variant)` — pulls one credential from either source,
  for the per-item loop on the non-custodial path.
- Both order functions are redefined with **only the stock-pop part changed**;
  the other lines are identical to the live definition being replaced.

**Verification.**

```
legacy path  : legacy_array=20 → 18, popped=2          (no regression)
variant path : legacy_array=0  → before=3 after=1, popped=2, items=["secret-A","secret-B"]
```

`legacy_array=0` is exactly the condition that used to make checkout fail. After the fix,
buying through the UI succeeds: `POST /api/orders → 201`, order `PENDING`, and the ledger
balances — `user_wallet DR 192.78` = `escrow_holding CR 189.00` + `platform_fee CR 3.78`.

> **Lesson.** When a system migrates from an old store to a new one, the *write*
> path is usually updated before the *read* path. What's dangerous is that both
> "look correct": the UI reads the new source (stock shows), checkout
> reads the old source (stock empty). A test that only checks the display will never
> catch it — you have to actually complete a transaction.

## 18. Health 503 makes the UI pick the wrong payment rail

**Symptom.** When `/api/health` returns **503** (status `degraded`, e.g. the indexer
is lagging), checkout fails completely:

```
POST /api/orders → 409
{"error":"custodial checkout is disabled while ONCHAIN_WALLET_FUNDS=1 …",
 "code":"CUSTODIAL_RAIL_DISABLED"}
```

**Root cause** (`public/app.jsx`). The frontend's payment-mode flag is taken from
`/api/health`, but it's only processed when the response is 2xx:

```js
const r = await fetch('/api/health');
if (r.ok) {                       // ← 503 does NOT get in here
  const h = await r.json();
  if (h && h.onChainFunds) window.ONCHAIN_FUNDS = true;
}
```

`/api/health` deliberately returns **503 when degraded**, even though its body is still valid
JSON and still carries `onChainFunds`. Because 503 isn't `ok`, the body is never
read → `window.ONCHAIN_FUNDS` stays `false` → the UI offers the **custodial** path while
the server is in **on-chain** mode → every checkout is rejected. The failure is silent (the
`catch` block swallows it).

**Fix.** Read the body without checking `r.ok` — the status code signals degradation, not
an invalid response.

**Verification.** With `health=503`: before the fix `mode=ledger` → 409; after the fix
`mode=on-chain gate=25` → `POST /api/orders/checkout/prepare → 201`.

> **Lesson.** An HTTP status code and the validity of a body are two different things. Using
> `r.ok` as a precondition for parsing makes **every temporary degradation** change
> the application's behavior — and here what changed is the payment rail, so a
> small glitch in the indexer turns into "the user can't pay".

## 19. Non-custodial draft is born `SENT` — regression of 0048/0057

**Symptom.** `checkout/prepare` returns 201, but the next step always fails:

```
POST /api/orders/checkout/challenge → 409
{"error":"order status SENT cannot challenge (expected one of: PENDING)"}
```

**Root cause.** `create_non_custodial_order` pops stock and immediately sets
`status='SENT'` at **prepare** time — even though the buyer hasn't paid yet. This is exactly the bug
that 0048 already fixed, then 0056 reintroduced (it overwrote 0048's body with
0043-era logic because the signature is identical), and 0057 fixed again.

The impact goes beyond the 409: FIFO stock is cut at prepare, so **abandoned
drafts keep consuming the seller's stock**, and `credentials_vault_ref` is set before
any money moves.

**Fix (0079).** `create_non_custodial_order` is restored to the 0048/0057 semantics: the draft
is **always `PENDING`**, with no stock pop and no credentials. The pop + `SENT` + credentials
move to `auto_advance_instant_order`, which only runs after the buyer's tx approval
is verified.

**Also:** `auto_advance_instant_order` now uses `pop_one_stock_item`,
so it knows about **both** stock stores. Previously it only read
`product_stock_items`, so products with legacy stock failed at fulfil — that is, **after
the buyer had already paid**.

**Verification.** `prepare → 201` with a `PENDING` draft; `challenge` proceeds up to the
environment's limit (it needs a provisioned UCW — see the note below).

> **Lesson.** A migration that overwrites a function with an **identical signature** erases
> the previous fix with no warning at all. 0048 → 0056 → 0057 is three rounds
> of the same bug. An invariant ("the draft is always PENDING") lasts longer when
> written as an **assertion in the migration**, not just as a comment — which is why
> 0079 closes with `DO $$ … RAISE EXCEPTION` if the invariant no longer holds.

## 20. Stock-cutting function can be called without logging in — CRITICAL

**Symptom.** Anyone holding the public anon key (which is indeed sent to the browser)
can drain a seller's stock:

```
POST /rest/v1/rpc/pop_one_stock_item
  {"p_product_id":"1d4f0a8c-…","p_variant_label":"Default"}
→ 200 "NFLX-0006-1679"        ← a real credential, no login, no payment
```

**Root cause.** `pop_one_stock_item` is a `SECURITY DEFINER` function created
by migration 0079. Postgres grants `EXECUTE` to `PUBLIC` by default, so
the function is born callable by anon. Migration 0078 — the very one whose job is to close
this kind of hole — ran **before** 0079, so it never saw
the function, and its assertion had already passed.

**Why the tests didn't catch it.** The existing security tests only **read the text
of migrations 0077/0078**; not one of them checks the live database. A function
created after the automatic sweep passes every test while wide open.

**Fix.**
1. `0079` now does `REVOKE ALL … FROM anon, authenticated, public` on both of its
   new functions, so a fresh database is never exposed even for an instant.
2. `0080` re-runs the 0078 sweep (closing anything added afterwards)
   and repeats its assertion.
3. `scripts/tools/security-sweep.sh` checks the **live database**, not text:
   the list of `SECURITY DEFINER` functions callable by anon, tables without RLS, and
   three sensitive RPCs that must reject anon. Can be run with
   `npm run security:sweep`.

**Verification.** Before the fix: `200 "NFLX-0006-1679"`. After the fix:
`401 permission denied for function pop_one_stock_item`. The sweep was also tested in reverse —
with an anon grant deliberately added, the sweep reports the finding and exits with code 1.

> **Lesson.** A security invariant tested by reading migration files is an
> invariant that **isn't tested**. What guards it is a check against the actual
> state. Sweep 0078 is logically correct, but it only runs once
> at a single point in time — so every migration that adds a function must be followed by
> a sweep, or the function must revoke `PUBLIC` itself.

## Appendix: UI/UX testing with a browser

Up to this point the entire audit only touched the API. `lint:fe` only ensures a file can
be parsed — not rendered. A page can throw during render, or show
**the wrong page**, while the route still returns healthy HTML.

**`scripts/ui-smoke.mjs`** (Playwright) opens each page for two passes — anonymous and
logged in as Admin — then collects: uncaught exceptions, console errors,
failed requests, and screenshots.

### Three traps in the test itself

1. **`networkidle` is never reached** — the landing page loads a Coinbase attribution script
   (`cca-lite.coinbase.com`) that never finishes. Switch to `domcontentloaded`.
2. **`root.length > 500` isn't a ready signal** — the sign-in shell also satisfies it, so
   the screenshot is taken before the session finishes restoring and `/wallet` is marked ✅ even though
   it's showing sign-in. Switch to: wait until `window.ME.uid` is populated.
3. **A 401 on `/api/auth/me` is CORRECT** for an anonymous visitor — that's exactly how the app
   knows there's no session. Don't flag it. But the same 401 is **fatal** when logged in.

> **Lesson:** "the page rendered" ≠ "the page is correct". A test that only checks "there's content"
> will pass a page showing the wrong content. Screenshots plus marker-text checks
> are mandatory.

## Appendix: end-to-end escrow flow verification

Not a fix — this is **proof** that the money path actually works.

### The custodial flow traced

```
POST /api/wl/deals                → MENUNGGU  ✅ 201
POST /api/wl/deals/[id]/proceed   → ESCROW    ✅ 200   (SELLER, deposits collateral)
POST .../mark-paid                →            ✅ 201   (buyer)
POST .../confirm-payment          →            ✅ 201   (seller)
POST .../release                  → SELESAI    🔒 requires admin token (PIN + challenge)
```

### Ledger proven balanced

```
user_wallet    DR  20.400.000   ← buyer (price 20 + fee 2%)
user_wallet    DR      10.000   ← seller (collateral 0.01 USDC)
escrow_holding CR  20.410.000   ← total held
```

20.400.000 + 10.000 = 20.410.000 → **debit = credit**. The double-entry is correct, and the
wallet balances match (buyer 100jt → 79,6jt; seller 50jt → 49,99jt).

### Role model that's easy to misread

| Action | Role | Note |
|---|---|---|
| `proceed` | **SELLER** | and the **seller** deposits the collateral — by design: collateral = the seller's fraud insurance |
| `release` | **ADMIN/MM** | requires `X-Admin-Token` from `/api/admin/verify` (PIN + UCW challenge, 2FA) |
| `mark-delivered` / `confirm-receipt` | **non-custodial only** | requires `on_chain_deal_id` + an external wallet; a custodial deal finishes via `release` |

A `release` that requires 2FA isn't an obstacle — that's **exactly how it should be** for an action
that moves funds.

### Performance note

`/api/wl/deals/prepare` takes **~9 seconds** because it checks the on-chain balance.
`/api/wl/deals` (custodial) ~2.6 seconds.

### Note: field names

The API field names (`unitPrice`, `desc`, `collateral`) differ from the initial assumptions when
testing manually. The API **correctly** ignores foreign fields — but the default value that gets
silently used (`unitPrice: 0`) can read like a bug. Consider rejecting
unknown fields on write endpoints.

## Important notes for production

All these fixes were **run against the local database**. Before mainnet/deploy:

   holes #1–#3 are still open there — and that means all user data can be
   read by the public.
